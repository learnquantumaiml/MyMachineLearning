## Data Drift Detection

- This code is a simple “data drift detector” for a churn model and it checks whether the new data you’re seeing  
  in production looks statistically different from the data the model was trained on. 

In simple terms, it generates two datasets:

 - reference_df: simulates the “old” data the model was trained on.
 
 - current_df: simulates new data after some real‑world change (e.g., prices went up, more month‑to‑month contracts).
 
 - For numeric features (age, tenure_months, monthly_charges), it runs a Kolmogorov–Smirnov (KS) test:
      -> If the p‑value is below 0.05, it flags drift for that feature.
      
 - For the categorical feature (contract_type), it compares category proportions:
     -> If any category’s share changes by more than 10 percentage points, it flags drift.

At the end, it prints an overall verdict:

“Drift detected” → the input data distribution has changed enough to warrant re‑evaluation/retraining.

“No significant drift” → data still looks similar to training data.

What we can achieve from this?

 - Early warning system: Detect when your model’s input data is shifting before performance visibly degrades.

 - MLOps monitoring:
    -> Plug this logic into pipelines (e.g., Azure ML, scheduled jobs) to automatically monitor drift in production.

 - Decision support: 
    -> Use drift flags to decide:
        a) When to retrain the model.
        b) When to investigate business changes (e.g., pricing, promotions) that might be causing the shift.


To Conclude, In my Azure MLOps context, this pattern fits well as a monitoring step after deployment:
  ->  Run it on new batches, log the results, and trigger retraining or alerts when drift is detected.
